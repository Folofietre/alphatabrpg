# Plan — Player-selected playback speed per song

> Status: draft / proposal
> Date: 2026-05-26
> Depends on: muscle-memory / high-score shipped, Bradley-Terry roll engine in place.

## Goal

Replace the **automatic** speed pick (Speed stat ÷ song onset rate) with a **manual** per-song selector in the playlist. The player explicitly chooses how fast each tab plays. The trade-off:

- **Slow speed (e.g. 30%)** — easy roll on every beat (relative to player skill), low endurance drain, but a small high-score.
- **Comfortable speed (matches Speed stat / song onset rate)** — natural rolls, normal endurance, decent score.
- **Faster than comfortable** — Dexterity rolls penalised, endurance burns faster, but the **score reward scales up sharply** because the composite formula already multiplies by `playbackMultiplier`.

The Speed stat doesn't disappear — it becomes the **comfort threshold**: pick a song speed ≤ Speed/onsetRate and rolls happen at face value. Pick higher and you're in "stretching" territory.

---

## UX — per-song speed selector

A horizontal slider (or +/- buttons with a percentage label) on each playlist row, sitting next to the title:

```
═══ Playlist ═══
► Twinkle (current)         70%  ──●──────
  Mary Had a Little Lamb    100% ────────●
  Stairway to Heaven        45%  ──●──────  (your comfort: 38%)
```

- Slider range: **20% – 100%** (clamped — playing under 20% drags too much; over 100% is out of scope).
- Granularity: **5% steps**.
- **Tooltip on hover**: "Your comfort: X%" — derived from `min(100%, player.speed / scoreOnsetRate × 100)`. Helps the player see whether they're below, at, or above their natural ceiling.
- **Default when adding a tab**: equal to the player's *current comfort speed* for that song. So new players get the same auto-pick behaviour as today, and they can crank it up when they feel like a challenge.
- **Persisted per tab**: the last selected speed lives in `tabRecords[id].lastSpeed` so opening the same tab tomorrow restores your last choice.
- **Locked during a run**: once Play is pressed, all sliders in the queue freeze (just like score-switching is locked). Stop / Replay to change them.

## Roll mechanics — how the selected speed feeds the engine

### Comfort threshold (per song, per character)

```js
const comfortSpeed = Math.min(1, character.speed / scoreOnsetRate)
// e.g. character.speed = 100, scoreOnsetRate = 250 → comfort = 0.40
```

### Over-speed factor

```js
const selectedSpeed = tab.selectedSpeed       // 0.20 .. 1.00
const overSpeed = Math.max(1, selectedSpeed / comfortSpeed)
// At/under comfort → 1 (no penalty)
// Picking 2× comfort → 2
```

### Per-beat roll

The Bradley-Terry roll is unchanged in shape — we just divide `effectiveDex` by `overSpeed`:

```js
const dex = effectiveDexFor(character.dexterity, familiarity) / overSpeed
const chance = dex / (dex + beatDC)
```

Equivalent to multiplying the DC by `overSpeed`. Picking 2× your comfort speed effectively doubles each beat's difficulty. Picking exactly your comfort → identical to today. Picking under your comfort → no bonus (the floor is `overSpeed = 1` so under-speeding doesn't trivialise hard songs).

### Playback multiplier

The actual tempo at which alphaTab plays:

```js
api.playbackSpeed = selectedSpeed
```

Direct mapping — no character-derived clamping. The user is in charge.

### Endurance cost

`beatExhaustion` already depends on real-time beat duration. Since real time = `1 / (tempo × selectedSpeed)`, a faster pick → more cost per beat automatically. No code change needed.

### High score

`compositeScore(accuracy, playbackMultiplier, dc)` is unchanged. Because `playbackMultiplier === selectedSpeed`, the score scales as the user described:

| Selected speed | Score on a perfect run (DC 60) |
|---:|---:|
| 100% | ~1080 |
| 80% | ~966 |
| 50% | ~764 |
| 30% | ~592 |
| 20% | ~483 |

So 100% pulls the maximum from the song; lower picks earn meaningfully less. The square-root keeps the curve forgiving — you don't lose 50% of your score for picking 50% speed.

## What happens to the Speed character stat?

It stays, with two adjusted roles:

1. **Comfort baseline** (consumed by the over-speed factor above). The higher your Speed stat, the higher the speed you can safely pick before rolls get punishing. This is what gives Speed its meaning in the new system.
2. **XP growth** still works as today (+10 on completion, +1 on stop, 0 on exhaust). But the gain should also reward stretching: I propose **a bonus +5 Speed when the player completes a song with `selectedSpeed > comfortSpeed`** — you only grow Speed by pushing past your current limit. Players who always stay in comfort grow Speed only at the base rate.

## Edge cases

- **Custom file dropped** — has no `tabRecord`, so no cached onset rate or last speed. Initialise selectedSpeed to 100% (or to the just-computed comfort once the file parses). The dropzone path bypasses the playlist anyway, so just hard-code a single-song selectedSpeed in `useAlphaTab` for that case.
- **Player has very low Speed (30) and song has high onsetRate (500)** — comfort = 6%. The slider clamps at 20%, so even the lowest pick is 3.3× over comfort, dex divided by ~3.3. Brutal but consistent with the "you're not ready" framing.
- **`overSpeed` floor at 1** means under-comfort picks never *help*. Intentional — otherwise players could trivialise any song by slowing it down to 20% and roll high. Slowness reduces dex pressure relative to real-time difficulty, which is already baked into `beatDC`'s speedFactor.
- **Slider during chained playlist run** — currentIndex is locked, but future entries should also be locked (changing the slider mid-run while the next song is queued would be confusing). Lock the whole queue.
- **Replay from the post-session panel** — restarts using the same `selectedSpeed` per song. No reset.

## Decisions / questions for you

1. **Slider range 20–100%** — comfortable for most cases. Should we allow over 100% ("hyperspeed") for prestige-tier characters who want to push? My take: **no for v1**, can add later.
2. **5% granularity** — feels good. Want finer (1%)? Coarser (10%)?
3. **Default speed on a fresh tab = player's comfort.** Alternative: default to 100%, force the player to dial down. Comfort-default keeps the current "auto-fit" feel; 100% is more challenge-forward. I prefer comfort-default for new players, advanced players can crank up easily.
4. **+5 Speed bonus on completion above comfort** — yes/no? Without it, Speed becomes pointless to grow (since players never have to pick higher). With it, there's a real incentive.
5. **Display comfort marker on the slider** — recommended, but you might find it noisy on small screens. Toggle in settings, or always show?
6. **High score formula unchanged** — confirmed.
7. **Custom file dropzone default speed** — 100% or comfort? Custom files probably get played by curious players who want the full experience; **100%** feels right.
